# L2 端到端评测协议（阶段 0 任务 0.4）

> 目的：回答一个 **L1 回答不了**的问题 —— agent 拿着这套检索工具，**能不能把活干成**？
> L1 用确定性指标量"该找到的找到没"；L2 量"拿到东西之后有没有做成事"。

## 为什么不能照搬 RAGAS

RAGAS 四维里有两项（Faithfulness / Answer Relevancy）评的是**答案**——RiMCP 没有生成层，
那是 agent 层的事。所以 L2 只把这四维当作**评分维度**用在"子代理 + 工具"这个整体上，
而不是塞进检索器。四维的**判定方式**也按其原意改写：

| 维度 | 判定方式（本协议） | 对应 RAGAS |
|---|---|---|
| **忠实度** | 答案里每条论断，能否在它 **实际 `get_item` 取回的代码**里找到依据 | Faithfulness |
| **相关性** | 是否直接回答了原问题（而不是描述了一套相邻机制） | Answer Relevancy |
| **上下文召回** | 完成任务所需的全部信息，是否都被检索到（有没有关键部分完全没碰到） | Context Recall |
| **上下文精确** | 有用结果是否排在前列，而不是在噪声里翻找 | Context Precision |

## 流程

```
对 tests/l2-tasks.json 的每个任务：
  1. 工人子代理：只给 RiMCP 的 MCP 工具（rough_search / get_item / get_uses / get_used_by / grep）
     工具有 5~10 次调用预算；要求它给出答案 + 列出它读过的 itemId
  2. 记录：调用了哪些工具、每次的结果数、读了哪些 itemId、耗时
  3. 评委子代理：先看证据（工人读过的代码），再看结论，按四维打分 1~5
  4. 人工复核（LLM 评委有噪声，不能当唯一依据）
```

**工人子代理的提示词要点**（照抄，别加暗示）：

- 只说任务，**不说**该用哪个工具、更不说期望的类名（否则测的是提示词不是检索）
- 要求"结论必须标注依据：每个论断后面写清依据来自哪个 itemId"
- 要求"如果不确定就说不确定"

**评委子代理的提示词要点**：

- **先给证据、后给结论**，并要求逐条论断对应到证据
- 明确"证据里没有的论断算不忠实，即使它是对的"（这正是 Faithfulness 的定义）
- 输出为结构化四维分数 + 一句话理由 + 扣分点

## 评分与解读

- 每个任务输出 `{faithfulness, answerRelevancy, contextRecall, contextPrecision}`（1~5）
- 汇总：四维均值 + 总分（四维调和平均，与 RAGAS 一致）；**同时记录每个任务的工具调用次数与 0 结果次数**
- **只看趋势，不做绝对判定**：这是 LLM 评委，噪声大。任何一次"变好/变差"都要和 L1 指标对齐看
- **8 个任务全跑**，但结论只对"≥2 个任务同向变化"才下

## 与另外两层的关系

| 层 | 回答 | 何时跑 |
|---|---|---|
| L1 `bench` | 能不能找到（确定性、可归因、零成本） | 每次改动 |
| **L2 本协议** | agent 用这套工具能不能把活干成 | 里程碑（M1/M2） |
| L3 `telemetry` | 真实使用中到底怎么样 | 持续 |

> **L2 的一次意外收获**：为 L2 做能力探测时顺带发现线上 MCP 工具**静默返回 0 结果**
> （见 `docs/rag-upgrade-plan-2026-09.md` §15）。L1 跑了十几轮都没发现，
> 因为 CLI 每次都是新进程新配置 —— **跨进程状态只有 L2/L3 能碰到**。
